# Architecture Decision Records

## ADR-001 — Plain `ws` + custom authoritative rooms instead of Colyseus
**Status:** accepted (2026-10-29)
**Context:** The brief suggests Colyseus "or a justified alternative". Our needs: 2–4 players per room,
one host screen, small intent messages, a deterministic pure simulation we want to unit-test
without a framework, and per-recipient payloads (host gets world state, phones get only hints).
**Decision:** Node `http` + `ws` with a ~400-line room layer (`apps/server/src/room.ts`).
**Consequences:** + no schema codegen, full control of per-recipient messages, delta stations, rate
limiting, reconnection policy; + simulation is framework-free and runs identically in tests and in
the menu attract mode. − We own matchmaking/scaling concerns (single process; horizontal scaling
needs sticky routing by room code — see DEPLOYMENT).

## ADR-002 — Vanilla TypeScript DOM for menus, no React
**Status:** accepted
**Context:** Menus are a handful of screens; the 3D canvas owns the frame budget; phones must load fast.
**Decision:** small `h()` helper (`apps/web/src/common/dom.ts`).
**Consequences:** controller bundle ≈ 37 kB JS (gzip ≈ 13 kB) without Three.js. Revisit if UI grows.

## ADR-003 — Procedural original assets for v1
**Status:** accepted, PROVISIONAL assets
**Context:** No licensed 3D/audio library was provided; downloading third-party assets without
verified licences is not allowed.
**Decision:** characters, stations, food, decor, textures, icons, music and SFX are generated by our
own code. Every asset is listed in `docs/ASSETS.md` with status and replacement plan (GLB pipeline).
**Consequences:** fully licence-clean and functional; visual ceiling below a hand-modelled game.
The renderer depends only on small interfaces (`ChefRig`, `StationObject`, `FoodObject`) so GLB
models can replace builders one by one.

## ADR-004 — Near-isometric orthographic camera, yaw 0°, pitch 41°
**Status:** accepted
**Context:** Grid kitchens must stay readable for 4 players on a TV. A 45° yaw (true isometric) hides
station fronts behind each other and skews the joystick mapping.
**Decision:** orthographic, yaw 0°, pitch 41°, auto-fit to the kitchen bounds with a reserved band
for the order rail. Joystick up = away from the camera, so phone and screen directions match.
**Evidence:** pitch 52° looked flat and top-down in screenshots; 41° shows counter fronts and chefs.

## ADR-005 — Server-side contextual hints
**Status:** accepted
Phones show the exact action available (`Agafar hamburguesa`, `Tallar`, `Reparar planxa`) computed by
the same resolver that applies the action, so the phone never needs the world state.

## ADR-006 — Disconnection policy
**Status:** accepted
- Lobby: slot kept 45 s for reconnection with the session token (stored on the phone).
- In game: the chef stays in the kitchen, frozen, holding whatever it held. If connected participants
  drop below `min(2, starting players)` the game pauses (`pauseReason: 'disconnect'`) and resumes
  automatically when they return. With 3–4 players one disconnection does not pause.
- Host screen lost: game pauses; room kept 120 s for `host:resume` with the host token.
- A new socket resuming a session replaces the old one (no duplicate seats per token).

## ADR-007 — Local campaign progress
**Status:** accepted
Progress (stars/best) is stored in the host browser (`localStorage`) and sent on room creation; the
server validates shape/ranges and uses it only to unlock levels. It cannot alter a running game's
score. No accounts or personal data are stored server-side.

## ADR-008 — Static batching
**Status:** accepted
`mergeStatic()` merges static meshes per material at level load (draw calls 695 → 214 measured in
headless Chromium). Animated nodes opt out with `userData.dynamic = true`.

## ADR-009 — Public hosting on Render (free web service)
**Status:** proposed (2026-10-29)
**Context:** Asking every player to install Node and run commands is not acceptable for real use.
The server is a single Node process that already serves the client and the WebSocket on one port.
**Decision:** ship `render.yaml` (Blueprint, free plan, health check `/healthz`) and a generic
`Dockerfile`. Players only open a URL on the TV and scan the QR.
**Consequences:** + zero install for players, HTTPS/WSS by default. − Free plan sleeps after 15 min idle
(~1 min cold start) and rooms are lost on restart; upgrade to a paid instance for always-on.
**Verified:** a clean checkout builds and serves with Render's exact build/start commands. The
Dockerfile has not been built (no Docker in the dev environment).
